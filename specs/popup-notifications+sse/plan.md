# Plan: Popup Notifications + SSE

Source: `specs/popup-notifications+sse/spec.md`

Conventions confirmed from the codebase: `internal/job` is a free-function repository package over raw `*sql.DB` (no ORM, transactions for read-then-write races, per `internal/job/job.go`'s existing `Create`); `internal/session`/`internal/otp` are the precedent for small Redis-backed packages taking a `*redis.Client` directly; `internal/handler` depends only on small consumer-defined interfaces (`Pinger`, `SessionValidator`, etc. — never a concrete type); Go tests are table-driven with `httptest`, integration tests gated on `TEST_DSN`/`TEST_REDIS_ADDR` (skip if unset); frontend tests are Vitest + Testing Library, `web/src/ui/` primitives each get their own `*.test.tsx`. `analysis_jobs.status` is already `VARCHAR(32)` (no enum) — **no DB migration needed anywhere in this plan.**

Two conventions this plan introduces and reuses across steps, called out once here: (1) **jsdom has no native `EventSource`** — every frontend test touching it must `vi.stubGlobal("EventSource", <mock class>)`; there is nothing to polyfill in production code, only in tests. (2) **testing a handler that loops until its request context is cancelled** (the SSE handler) means calling `ServeHTTP` in a goroutine, driving it via a cancellable `context.Context` on the request, and asserting on `httptest.ResponseRecorder.Body` after cancelling — a pattern with no precedent yet in this repo, spelled out in step 3.

## Steps

1. **`internal/job` — `UpdateStatus` and `ListByStatus`**
   - Files: `internal/job/job.go`, `internal/job/job_test.go`
   - What: `var validTransitions = map[string][]string{"pending": {"processing"}, "processing": {"done", "failed"}}`. `UpdateStatus(ctx, db, jobID uint64, newStatus string) (Job, error)` — mirrors `Create`'s transaction pattern: `SELECT ... FOR UPDATE` the current row (return `ErrNotFound` if missing), reject with a new `ErrInvalidTransition` if `newStatus` isn't in `validTransitions[current.Status]` (covers spec criterion 11 — including a no-op like `processing→processing`, which isn't in the allowed-target list either), else `UPDATE` and reload+return the full updated `Job` (so the caller has `UserID` for publishing, without a second query). `ListByStatus(ctx, db, status string) ([]Job, error)` — like `ListByUser` but filtered by `status` with **no `user_id` filter** (doc-comment explicitly notes this is a worker-internal query, not exposed through any handler, so it doesn't fall under CLAUDE.md's per-handler `user_id` rule).
   - Test first (red), added to `job_test.go` (same `testDB`/`mustCreateUser`/`cleanupJob` helpers, `TEST_DSN`-gated): `TestUpdateStatus_PendingToProcessing`, `TestUpdateStatus_ProcessingToDone`, `TestUpdateStatus_ProcessingToFailed`, `TestUpdateStatus_RejectsPendingToDone` (skips `processing`), `TestUpdateStatus_RejectsSameStatus` (`processing→processing`), `TestUpdateStatus_NotFound`, `TestUpdateStatus_RejectsSecondTransitionAfterFirstApplied` (call twice: `processing→done` succeeds, a second `processing→done` on the now-`done` job fails — this is spec edge case 7's double-transition guard, exercised sequentially rather than with real goroutine concurrency, matching this file's existing style). `TestListByStatus_AcrossUsers` (two users, confirms both appear, no user filtering), `TestListByStatus_Empty`.
   - Implement until green.
   - Verify: `TEST_DSN=... go test ./internal/job/... -run TestUpdateStatus -v` and `-run TestListByStatus -v`; `go build ./...` (compiles without a DSN too).

2. **`internal/jobevents` — Redis pub/sub wrapper (new package)**
   - Files: `internal/jobevents/jobevents.go`, `internal/jobevents/jobevents_test.go`
   - What: `const Channel = "job_status_updates"`; `type StatusChanged struct { JobID uint64 \`json:"job_id"\`; UserID uint64 \`json:"user_id"\`; Status string \`json:"status"\` }`; `func Publish(ctx, client *redis.Client, event StatusChanged) error` (marshal + `client.Publish(ctx, Channel, b).Err()`). `type Broadcaster struct` holding a `map[uint64][]chan []byte` (per-`userID` list of subscriber channels) behind a `sync.Mutex`, with `Subscribe(userID uint64) (events <-chan []byte, unsubscribe func())` (adds a buffered channel — buffer size documented, e.g. 8 — to the registry, returns an unsubscribe closure that removes it) and `dispatch(raw []byte)` (unmarshals `StatusChanged`, non-blocking-sends — `select { case ch <- raw: default: }` — to every channel registered for that `UserID`, so one slow/stuck consumer never blocks another user's delivery or the Redis read loop). `Run(ctx context.Context, client *redis.Client) error` subscribes once to `Channel` and calls `dispatch` for every incoming message until `ctx` is cancelled.
   - **Design split for testability**: `dispatch` is a plain method taking `[]byte`, with zero Redis dependency — the fan-out/registry logic (the part with real bugs to catch: multiple subscribers, wrong-user isolation, unsubscribe cleanup, non-blocking send) is unit-tested by calling `dispatch` directly. Only `Run`'s "read from an actual Redis subscription" plumbing needs a real Redis, gated on `TEST_REDIS_ADDR` like `internal/otp`/`internal/session`.
   - Test first (red): `TestBroadcaster_DispatchDeliversToSubscribedUser`, `TestBroadcaster_DispatchIsolatesOtherUsers` (User B's channel gets nothing from a User A event — this is spec edge case 1 / criterion 3's unit-level proof), `TestBroadcaster_MultipleSubscribersSameUser` (two tabs — both channels receive it, per edge case 3), `TestBroadcaster_UnsubscribeStopsDelivery`, `TestBroadcaster_SlowConsumerDoesNotBlock` (fill one subscriber's buffered channel, then dispatch again and assert a *different* user's channel still receives promptly — proves the non-blocking send). `TestRun_PublishSubscribeRoundTrip` (`TEST_REDIS_ADDR`-gated): real `Publish` → real `Run` in a goroutine → assert `dispatch` fired (observable via a `Subscribe`d channel).
   - Implement until green.
   - Verify: `go test ./internal/jobevents/... -race` (the mutex-guarded registry is exactly the kind of code the race detector exists for); `TEST_REDIS_ADDR=... go test ./internal/jobevents/... -run TestRun -v`.

3. **`internal/handler` — `JobStreamHandler` (SSE endpoint)**
   - Files: `internal/handler/jobs_stream.go`, `internal/handler/jobs_stream_test.go`
   - What: `JobEventSubscriber interface { Subscribe(userID uint64) (events <-chan []byte, unsubscribe func()) }` (consumer-defined, satisfied by `*jobevents.Broadcaster`, per CLAUDE.md's handler-interface rule). `JobStreamHandler struct { Events JobEventSubscriber; Sessions SessionValidator }` (reuses the existing `SessionValidator` interface from `auth.go` — no new session-validation interface). `ServeHTTP`: read `userID` from `UserIDFromContext` (already validated once by `SessionMiddleware` wrapping this route, same as every other `/jobs*` route); type-assert `http.Flusher`; set `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, write `200`, flush; `Subscribe(userID)`, `defer unsubscribe()`; read the session cookie via the existing unexported `sessionCookieName` const (same package, no new export) for the periodic re-validation; loop on `select` across `r.Context().Done()` (return — client disconnected or api shutting down), the event channel (write `event: job_status\ndata: <json>\n\n`, flush), and a `60*time.Second` ticker (call `h.Sessions.Validate(r.Context(), cookieValue)`; return if it errors — closes the stream per spec criterion 7).
   - **Test approach** (no precedent in this repo — spelled out here for the implementer): each test builds a `context.WithCancel`-backed request, runs `h.ServeHTTP(rec, req)` in a goroutine, drives the scenario (send on a stub subscriber's channel, or advance a fake clock for the re-validation ticker — inject the ticker interval as a struct field, e.g. `RevalidateInterval time.Duration`, defaulting to 60s in production wiring but set to a few milliseconds in tests so they don't take a real minute), `cancel()` the request context, join on a "done" channel closed when `ServeHTTP` returns (with a `t.Fatal` timeout guard, e.g. 1s, so a bug can't hang the suite), then assert on `rec.Body.String()`.
   - Test first (red): `TestJobStreamHandler_Unauthenticated401` (via the existing `SessionMiddleware` wrapper, mirroring `auth_test.go`'s `TestSessionMiddleware` table — no session cookie ⇒ 401, handler never reached, matching criterion 10). `TestJobStreamHandler_DeliversEvent` (stub subscriber sends one message, body contains `event: job_status` and the JSON payload). `TestJobStreamHandler_ClosesOnClientDisconnect` (cancel the request context, handler returns promptly, `unsubscribe` was called — stub subscriber tracks this). `TestJobStreamHandler_ClosesOnRevalidationFailure` (short `RevalidateInterval`, `stubSessionValidator` returns an error, handler returns without the test needing to wait 60 real seconds).
   - Implement until green.
   - Verify: `go test ./internal/handler/... -run TestJobStreamHandler -race -v` (goroutine + shared recorder — race-check this one specifically).

4. **Wire into `cmd/api` and `cmd/worker`**
   - Files: `cmd/api/main.go`, `cmd/api/main_test.go`, `cmd/worker/main.go`, `cmd/worker/main_test.go`
   - What, `cmd/api/main.go`: construct one `jobevents.Broadcaster{}` in `main()`, launch `go broadcaster.Run(ctx, redisClient)` (reuse the existing `redisClient` already connected for sessions/OTP — no second Redis connection), register `mux.Handle("GET /jobs/stream", handler.SessionMiddleware(&handler.JobStreamHandler{Events: broadcaster, Sessions: sessionStore, RevalidateInterval: 60*time.Second}, sessionValidator))` in `buildServer` (add a `broadcaster jobevents_handler.JobEventSubscriber`-typed... — actually: `buildServer`'s signature gains one new parameter, `jobEvents handler.JobEventSubscriber`, following the same pattern as every other dependency already threaded through it).
   - What, `cmd/worker/main.go`: `runLoop`'s signature changes from `runLoop(ctx)` to `runLoop(ctx, db *sql.DB, redisClient *redis.Client)` (breaks the existing `TestRunLoop_Cancels` call site — update it, don't leave it broken). Replace the `slog.Info("worker idle")` tick body with: `pending, _ := job.ListByStatus(ctx, db, "pending")`; `processing, _ := job.ListByStatus(ctx, db, "processing")` (both snapshotted **before** any writes this tick — this ordering is load-bearing: it's what gives a job exactly one 5-second tick in `processing` before advancing to `done`, rather than jumping straight through in the same tick it was created — see spec criterion 8); for each `pending` job, `job.UpdateStatus(ctx, db, j.ID, "processing")` then `jobevents.Publish(...)`; for each (pre-tick) `processing` job, `job.UpdateStatus(ctx, db, j.ID, "done")` then `jobevents.Publish(...)`. A publish error is logged (`slog.Error`) and does not stop the tick or crash the process (spec edge case 6 — Redis being briefly unavailable degrades notifications only, not job progression).
   - Test first (red): `cmd/api/main_test.go` — extend the existing routes-registered test with an unauthenticated `GET /jobs/stream` ⇒ 401 case (same shape as the existing `/jobs` cases). `cmd/worker/main_test.go` — update `TestRunLoop_Cancels` for the new signature (pass `nil, nil` since it cancels before ever touching them); add `TestProcessTick_AdvancesPendingAndProcessingSeparately` — extract the per-tick body into a standalone `processTick(ctx, db, redisClient)` function (so it's callable without waiting on the real ticker) and test it `TEST_DSN`+`TEST_REDIS_ADDR`-gated: seed one `pending` and one already-`processing` job, call `processTick` once, assert the pending job is now `processing` (not `done` — proves the snapshot-before-write ordering) and the already-processing job is now `done`.
   - Implement until green.
   - Verify: `go test ./cmd/... ./internal/...`; `go build ./cmd/...`.

## Order

1 (`internal/job`) → 2 (`internal/jobevents`, depends on nothing from 1 but is needed by 3 and 4) → 3 (`internal/handler`, depends on 2's `JobEventSubscriber` shape) → 4 (wiring, depends on 1+2+3 all existing) → 5 (nginx, independent of Go work, can happen any time after 4 but is listed after so the thing it's unblocking — real SSE traffic — already exists to verify against) → 6 (`Toast.tsx`, independent of all Go work and of step 7) → 7 (frontend SSE client, depends on 6's `useToast` and reuses `AuthContext`/`router.test.tsx` patterns) → 8 (full-suite check). Steps 1–4 (backend) and step 6 (frontend `Toast.tsx`) have no dependency on each other and could be built in either order or in parallel; 7 depends on both 4 (the real endpoint contract) and 6.

No DB migration step — `analysis_jobs.status` is already an unconstrained `VARCHAR(32)`; the new transition guard (`validTransitions`) is application-level only, in step 1.

## Risks

- **jsdom has no `EventSource`.** Steps 7's tests will hit `ReferenceError: EventSource is not defined` unless every test file that touches the hook stubs it globally first (`vi.stubGlobal`). Called out at the top of this plan and repeated in step 7 so it isn't rediscovered mid-implementation.
- **Testing an infinite-loop `select` handler synchronously is unusual for this codebase.** Step 3's goroutine + cancellable-context + timeout-guarded join pattern is new here; if the implementer instead tries to call `ServeHTTP` and wait for it to return normally (as every other handler test in this repo does), the test will hang. Plan B if step 3's tests are flaky in CI: increase the timeout guard and/or switch the stub subscriber's channel operations to be explicitly synchronized (e.g. a buffered channel of size 1 with a test-side `<-doneSignal` after sending) rather than relying on goroutine scheduling order.
- **Worker's snapshot-before-write ordering is subtle and easy to accidentally "fix" into a bug.** A future edit that merges the `pending`/`processing` queries into one, or re-queries mid-tick, would silently let a job skip straight from `pending` to `done` in one tick, violating spec criterion 8 (each transition needs its own event). `TestProcessTick_AdvancesPendingAndProcessingSeparately` (step 4) exists specifically to catch that regression — do not weaken or remove it.
- **`Broadcaster`'s registry is shared mutable state accessed from the Redis-read goroutine and every open SSE connection's goroutine.** A missed lock or an unbuffered/blocking send in `dispatch` could deadlock the entire notification pipeline for every user, not just one. Mitigated by the non-blocking-send design (step 2) and `-race` in that package's verify command — treat any `-race` failure here as blocking, not a flake to retry past.
- **Redis pub/sub message ordering/delivery is best-effort**, consistent with the spec's own Non-scope (no backfill). If `docker compose`'s manual SSE smoke test (step 5) shows events arriving out of order across a fast pending→processing→done sequence, that's expected given the architecture, not a bug — do not add ordering guarantees not asked for in the spec.
