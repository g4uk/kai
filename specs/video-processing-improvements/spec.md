# Spec: Video Processing Improvements

## Problem

`specs/video-processing` shipped a synchronous download → probe → analyze pipeline with retry/backoff, but running it against real kumite footage surfaced five gaps. Coaches watching a job see no signal between `processing` and `done`/`failed` beyond those two status flips, so a long job looks stalled with no indication of which stage it's in. A downloaded file is never checked for completeness before analysis, so a truncated download surfaces as a confusing ffprobe/ffmpeg failure instead of a clear reason. Motion-detection sensitivity (`gridCell`, `motionThresholdPerPair`, `minRegionCells`) is hardcoded, so retuning it for real-world footage requires a code change and redeploy. Failure text written to `job_summaries` is a raw wrapped Go error string that can include internal temp-directory paths and unfiltered subprocess stderr. Most consequentially, `detectParticipants` treats **every** detected moving region as a participant — so a real kumite match, which always has an active referee and often corner judges or a moving crowd in frame, produces `participants` rows for people who aren't fighters, corrupting every downstream per-participant metric. This feature closes those five gaps.

## Scope

1. **Stage-level progress reporting.** `video.Pipeline` reports which stage (`downloading`, `probing`, `analyzing`) a processing attempt is in via a new injected callback/interface. `cmd/worker/main.go` publishes one lightweight "stage changed" event per transition to `jobevents.Channel` — a new payload shape alongside the existing `StatusChanged` event, not a replacement for it. These events are ephemeral pub/sub only: `job.status` in the database and `validTransitions` (`pending→processing→done/failed`) are completely unchanged; a stage event is never persisted and is not a checkpoint. `internal/jobevents`'s existing `Broadcaster.dispatch` fans these out per-`UserID` exactly as it does `StatusChanged` today.

2. **Download/video-integrity validation.** After `yt-dlp` reports success and before `ffprobe` metadata extraction, a new validation step confirms the downloaded file is non-empty and passes a basic ffprobe-based integrity check (openable, reports at least one video stream). A file that fails this check is a **new, distinct error category** (not `ErrVideoTooShort`) — since a truncated/incomplete download is typically a transient network issue, it is retried under the existing retry policy (unlike `ErrVideoTooShort`, which reflects the source video's actual duration and is the same on every attempt).

3. **Configurable motion-detection thresholds.** `gridCell`, `motionThresholdPerPair`, and `minRegionCells` (currently unexported constants in `internal/video/analyzer.go`) become `FFMPEGAnalyzer` struct fields, following the existing `SampleFPS` pattern — each defaults to today's value when zero/unset. `cmd/worker/main.go`'s `main()` reads three new optional env vars (`MOTION_GRID_CELL_PX`, `MOTION_THRESHOLD_PER_PAIR`, `MOTION_MIN_REGION_CELLS`) to populate them, so an operator can retune sensitivity via `docker-compose.yml` without a code change or rebuild.

4. **Two-fighter detection (top-N by sustained motion).** `detectParticipants`'s region scoring gains a **persistence score** per region: the fraction of frame-pairs in which that region's cells were actively moving, computed per-pair (not just accumulated across the whole video as today). Fighters move near-continuously through a match; a referee's motion is comparatively bursty (brief point calls, otherwise relatively still) — ranking by persistence, not raw accumulated activity, favors the fighters. After scoring, only the top `MaxParticipants` regions by persistence score (ties broken by total accumulated activity score) are kept; `MaxParticipants` defaults to **2** and is configurable via a new `MAX_PARTICIPANTS` env var for non-standard footage, without a code change. This is a heuristic — explicitly **not** ML/pose-estimation, carrying forward `specs/video-processing`'s Non-scope decision (locked in as the MVP approach; see Constraints on accuracy).

5. **Clearer, non-leaking failure summaries.** `failureSummary` in `cmd/worker/main.go` categorizes the pipeline error into one of a small fixed set of human-readable reasons ("download failed," "downloaded file was incomplete or corrupt," "video too short or corrupt to analyze," "analysis timed out," "analysis failed") instead of interpolating the raw wrapped Go error (`%v`) — which today can include internal temp-directory paths and raw `yt-dlp`/`ffmpeg` stderr — into `job_summaries.summary`, which is returned verbatim to any authenticated owner of the job via `GET /jobs/:id` and rendered in `JobResultsPage.tsx`. The full original error, unfiltered, continues to be logged via `slog` server-side for operator debugging — only what's persisted/API-facing changes.

## Non-scope

- **ML/pose-estimation-based person detection.** Locked in as an explicit MVP decision: the top-N-by-persistence heuristic is the approach for this spec. A real person-detection model is a candidate follow-up if the heuristic proves insufficient on real match footage, not part of this spec.
- **New job statuses or a DB schema/migration change.** `job.status` stays `pending`/`processing`/`done`/`failed`; stage-progress events are published, never persisted; `participants`/`participant_metrics`/`job_summaries` schema is unchanged.
- **Concurrent/parallel job processing.** Still out of scope per `docs/decisions.md` #004, unchanged from `specs/video-processing`.
- **Per-job or per-user configuration of thresholds/`MaxParticipants` via API or UI.** The new env vars are operator/deployment-level config only; no request/response shape in `internal/handler` changes.
- **First-class support for more-than-2-fighter formats (e.g. team events).** `MaxParticipants` is configurable, but this spec's acceptance criteria and tests target the 2-fighter case only.
- **Fighter identity/name assignment.** Output remains `"Participant 1"`/`"Participant 2"` labels in detection order; no cross-video identity linking (unchanged from `specs/video-processing` Non-scope).
- **Re-processing already-completed jobs under new thresholds.** Threshold/`MaxParticipants` changes only affect jobs processed after a config change and worker restart; no backfill/re-analysis mechanism is introduced.
- **Crash/restart recovery for jobs stuck mid-`processing`.** Unchanged from `specs/video-processing` Non-scope; a stage event is not a checkpoint and does not change this.

## Acceptance criteria

1. When a processing attempt moves from one pipeline stage to the next (`downloading`→`probing`→`analyzing`), then a stage-change event is published to `jobevents.Channel` containing the job's ID, user ID, and the new stage name — distinct from, and in addition to, the existing `pending`/`processing`/`done`/`failed` `StatusChanged` events.
2. When an SSE client is subscribed to a job's events during a processing attempt, then it receives one stage event per transition, in stage order, and `job.status` in the database is never modified by a stage event.
3. When `yt-dlp` exits successfully but the resulting file is 0 bytes or fails the ffprobe-based integrity check, then that attempt fails with a reason distinguishing "corrupt/incomplete download" from both a generic download failure and `ErrVideoTooShort`, and the attempt is retried under the existing 3-attempt/backoff policy (not treated as immediately non-retryable).
4. When all 3 attempts fail due to a corrupt/incomplete download, then the job transitions to `failed` and `job_summaries.summary` states the download was incomplete/corrupt in human-readable text — not a raw ffprobe/exec error string.
5. When `MOTION_GRID_CELL_PX`, `MOTION_THRESHOLD_PER_PAIR`, and `MOTION_MIN_REGION_CELLS` are set to non-default values, then `FFMPEGAnalyzer`/`detectParticipants` uses those values instead of today's hardcoded 32px/15.0/2, verified by a test where a changed threshold changes which regions are detected as moving.
6. When those three env vars are unset, then analyzer behavior is identical to today (32px grid, 15.0 per-pair threshold, 2 min region cells) — no behavior change for a deployment that sets none of them.
7. When motion analysis detects more than `MaxParticipants` distinct moving regions (e.g. 2 fighters + 1 referee), then exactly `MaxParticipants` `participants` rows are persisted — the top-scoring regions ranked by persistence score (fraction of frame-pairs each region was active in), not by raw accumulated activity sum alone.
8. When motion analysis detects `MaxParticipants` or fewer distinct moving regions, then all detected regions (0, 1, or up to `MaxParticipants`) are persisted unchanged — the cap never invents participants that weren't detected.
9. When `MAX_PARTICIPANTS` is set to a value other than 2 (e.g. 1), then that many top regions by persistence score are persisted instead of 2, verified by a test with 3 detected regions and `MAX_PARTICIPANTS=1` producing exactly 1 persisted participant.
10. When `MAX_PARTICIPANTS` is unset, then exactly 2 participants are kept when more than 2 regions are detected (today's default becomes 2, not "all regions" as it is before this spec).
11. When a processing attempt fails for any reason (download failure, corrupt download, too-short video, timeout, analysis failure), then `job_summaries.summary` contains one of the fixed human-readable category strings and never includes raw subprocess stdout/stderr text or filesystem temp-directory paths, while the complete underlying error (including subprocess output) is still logged via `slog` for operator visibility.
12. When `go build ./cmd/...` runs, then the worker binary compiles with zero errors.
13. When `docker compose up --build` runs (new env vars left unset, matching today's defaults) and a real job is submitted against a short real YouTube video with exactly 2 people moving in frame, then the job reaches `done` with exactly 2 `participant_metrics` rows.

## Edge cases

1. **Referee/official present but comparatively still, alongside 2 active fighters** — the primary motivating case; top-`MaxParticipants` selection by persistence score excludes the referee's region. Covered by criterion 7. (Heuristic accuracy is not guaranteed 100% — see Constraints.)
2. **Exactly `MaxParticipants` regions detected** — no filtering needed, both/all kept. Covered by criterion 8.
3. **Fewer than `MaxParticipants` regions detected** (0 or 1 fighter visibly moving) — all detected regions kept; no padding or invented participants. Covered by criterion 8.
4. **Download appears to succeed (`yt-dlp` exit 0) but produces a 0-byte or truncated file** — treated as corrupt/incomplete, retried, distinguishable in `job_summaries` from `ErrVideoTooShort`. Covered by criteria 3/4.
5. **SSE client's subscription drops mid-job, then a stage event is dispatched** — existing `Broadcaster` non-blocking-send/drop-on-full-buffer behavior (spec `popup-notifications+sse` edge case 6) applies unchanged to stage events; no new blocking risk is introduced.
6. **A motion-detection env var is set to an invalid/unparseable value** — falls back to the documented default with a logged warning, mirroring `cmd/worker/main.go`'s existing invalid-`PROCESSING_TIMEOUT` handling.
7. **Worker restart between the download stage and the probe stage of one job** — `specs/video-processing`'s Non-scope (crash/restart recovery) still applies unchanged; a stage event is not a persisted checkpoint, so the job remains in `processing` indefinitely per the existing documented limitation.
8. **A region's persistence score ties with another region's** — tie-break by total accumulated activity score (higher wins), so region selection stays deterministic given identical input frames.

## Constraints

- Security: `job_summaries.summary`/API-facing failure text never includes raw subprocess output or filesystem paths (closes a minor info-leak — today's `fmt.Sprintf("processing failed: %v", err)` can surface internal temp-directory paths and raw `yt-dlp`/`ffmpeg` stderr verbatim to any authenticated user who owns the job).
- Compatibility: no DB migration — `participants`/`participant_metrics`/`job_summaries` schema and `job.validTransitions` are unchanged; stage-progress events are ephemeral pub/sub only.
- Accuracy: the top-`MaxParticipants`-by-persistence heuristic is not guaranteed to exclude a referee/official from every video — it is a heuristic improvement over "keep every detected region," not a guarantee. If it proves insufficient on real match footage, a real person-detection model is a candidate follow-up spec (see Non-scope) — decided against for this MVP due to added model dependency, likely breaking the current `CGO_ENABLED=0` pure-Go build, and added per-job CPU cost on a single Hetzner VPS.
- Deployment: all four new env vars (`MOTION_GRID_CELL_PX`, `MOTION_THRESHOLD_PER_PAIR`, `MOTION_MIN_REGION_CELLS`, `MAX_PARTICIPANTS`) are optional; leaving all unset must reproduce today's analyzer-threshold behavior exactly, except `MaxParticipants` which changes the default cap from "unlimited" to **2** (criterion 10) — this is an intentional behavior change (the entire point of this spec), called out explicitly here rather than left implicit.
- Performance: persistence-score computation reuses the same per-frame-pair loop `accumulateCellDiffs` already runs (tracking per-pair activity in addition to the accumulated total, not a second pass over frames) — no additional `ffmpeg`/`ffprobe` invocations are introduced.
