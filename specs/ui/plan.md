# Plan: UI

Source: `specs/ui/spec.md`

Conventions confirmed from the codebase before planning:
- This is the **first frontend code in the repo** — `web/` does not exist yet. `.claude/skills/frontend/SKILL.md` is still the generic template (`<!-- EDIT_ME -->` placeholder), so its rules (feature-folder structure, Testing Library behavior tests, no `any`, no UI-library dependency without approval, global store only after a 2nd consumer) are followed as written, but there is no prior React code in this repo to pattern-match against.
- Backend contract (already implemented, confirmed by reading `internal/handler/auth.go` and `internal/handler/jobs.go` directly, not just their specs):
  - `POST /auth/otp/request` — body `{"phone_number"}`, `202` on success, `400` on bad phone, `429` on rate limit. **Error bodies are plain text** (`http.Error` writes `Content-Type: text/plain`, not JSON) — e.g. `invalid phone_number`, `too many requests`.
  - `POST /auth/otp/verify` — body `{"phone_number","code"}`, `200` + `Set-Cookie: session_id=...; HttpOnly; Secure; SameSite=Strict` on success, `401` plain-text `invalid or expired code` otherwise (the API deliberately does not distinguish mismatch/expired/too-many-attempts in the response).
  - `POST /auth/logout` — no body needed, always `200`, clears the cookie (`Max-Age=0`); safe to call even with no session cookie (idempotent no-op per `internal/handler/auth.go`'s `LogoutHandler`).
  - `GET /jobs` — `200` `{"jobs":[...]}` (`Job{id, youtube_url, status, created_at, updated_at}`), `[]` never `null`. `401` plain text if unauthenticated.
  - `POST /jobs` — body `{"youtube_url"}`, `201` + `Job` on success, `400` plain text `invalid youtube_url`, `409` plain text `duplicate job`.
  - `GET /jobs/:id` — `200` + `JobDetail` (`Job` fields + `participants: Participant[]` + `summary: string|null`), `Participant{id, label, metrics: Metric[]}`, `Metric{key, value}` (value is a JSON number). `400` on non-numeric id, `404` plain text `not found` for both nonexistent and foreign-tenant (indistinguishable, per spec criterion 14/backend criterion 13).
  - No `job_summaries`/status-transition endpoint exists yet (worker spec deferred) — `done`/`failed`/`pending`/`processing` values all come from whatever `status` the DB row currently has; the UI never triggers a transition.
  - **No OpenAPI/schema file exists anywhere in the repo** — the wire shapes above were read directly from the handler source, not generated from a spec. There is nothing to codegen a client from.
- `docker-compose.yml` currently has `mysql`, `redis`, `api` (port `8080:8080`, healthcheck via `curl /healthz`), `worker`. Root `Dockerfile` is a single multi-stage file with `builder` → `api`/`worker` target stages selected via `docker-compose.yml`'s `build.target`.
- `docs/decisions.md` has 5 entries (001–005); this spec explicitly requires a new entry per its final Constraints bullet and the Note under Non-scope.
- `docs/surface-map.md` (referenced by `CLAUDE.md` as required pre-reading for cross-module tasks) does not exist in this repo yet — noted, not blocking; not this spec's job to create it.

Concrete values not pinned by the spec, decided here (flag if wrong):
- **Toolchain**: React 18 + TypeScript, built with **Vite** (`vite build` only — the spec's non-scope explicitly excludes a Vite-dev-server Compose service, but the build tool itself is an implementation detail, not a Compose service). Package manager: npm (`package-lock.json` committed).
- **Test stack**: Vitest + `@testing-library/react` + `@testing-library/user-event`, jsdom environment — the closest TS/React equivalent to the Go repo's "plain `testing`, table-driven, real dependencies over mocks" convention: component tests render real components and assert on rendered behavior (Testing Library), a hand-written `fetch` stub (not a mocking framework) stands in for the network per frontend skill rule 3 ("External APIs: interface + fake inside the package").
- **Routing**: `react-router-dom`. This is a new dependency beyond bare React; flagging per frontend skill rule 8 ("no UI library/dependency without human approval") — routing is structural, not a UI/component library, but it's still new and worth a one-line sign-off before Step 1 lands it in `package.json`.
- **Styling: Tailwind CSS** — explicitly requested, so this is the one dependency in this plan with standing human approval already in hand for frontend skill rule 8 (no sign-off gap, unlike `react-router-dom` above). Version: Tailwind v4 via the official `@tailwindcss/vite` plugin — v4's CSS-first setup needs no `tailwind.config.js`/`postcss.config.js`, just the plugin registered in `vite.config.ts` and one `@import "tailwindcss";` line in `web/src/index.css`, imported once from `main.tsx`. (If v3 is actually required for some compatibility reason, the fallback is `tailwindcss`/`postcss`/`autoprefixer` + a `tailwind.config.js` `content` glob over `web/src/**/*.{ts,tsx}` — a small, contained swap, not a redesign.) Tailwind is a utility-class engine, not a component/widget library (no prebuilt `<Button>`/`<Modal>` primitives), so it doesn't reopen the "which design system" question — components are still hand-written JSX, just styled with utility classes instead of hand-rolled CSS.
- **No component/UI library** (no MUI/Chakra/etc.) and **no global state library** (no Redux/Zustand) — Tailwind utility classes (see above) + `useState`/`useEffect` + one small custom hook per screen. Justified by YAGNI (4 screens, no cross-screen shared mutable state beyond "is there a session," which a single `AuthContext` covers) and it avoids the rule-8 approval question for anything beyond routing (Tailwind's already cleared; `react-router-dom` is the one still-open sign-off below).
- **No TanStack Query / SWR** — the spec's non-scope explicitly excludes polling/real-time updates and caching-across-navigation subtleties are minimal (reload-to-refresh is the stated model), so a plain `fetch`-in-`useEffect` hook per screen is simpler than adopting a server-cache library for four one-shot requests. Revisit only if a second screen needs the same in-flight job's data simultaneously (2nd-consumer YAGNI gate).
- **Typed API client without codegen**: since no OpenAPI/schema exists to generate from, frontend skill rule 3 ("API calls only through the generated/typed client") is satisfied by one hand-written module, `web/src/api/client.ts`, holding every fetch call and the shared response/error types (`web/src/api/types.ts`) — components never call `fetch` directly. This is the "typed client," just not a generated one.
- **Error parsing**: because 4xx/429 bodies are `text/plain` (confirmed above), the client reads `response.text()` on non-2xx responses and surfaces that raw string as the inline error message (e.g. "invalid youtube_url") — no JSON error envelope to parse.
- **nginx service naming/ports**: new Compose service `web`, `build.target: web` in the existing root `Dockerfile` (a new final stage added there, not a second Dockerfile, to match the existing single-multi-stage-file convention), host port `8081:80` (chosen to avoid colliding with `api`'s existing `8080:8080` mapping — adjustable, not load-bearing).
- **Healthcheck**: `nginx:alpine` has no `curl`; use `wget --spider` (BusyBox `wget` is present in `nginx:alpine`) — `test: ["CMD", "wget", "--spider", "-q", "http://localhost/"]`, matching the existing services' `interval`/`timeout`/`retries` shape.
- **Reverse proxy prefix stripping**: the SPA calls `/api/*` (per spec criterion 17/18 and the constraints), but the Go API's routes have no `/api` prefix (`POST /jobs`, not `POST /api/jobs`) — nginx's `location /api/ { proxy_pass http://api:8080/; }` (trailing slash on `proxy_pass` strips the `/api/` prefix before forwarding). Flagging because this is the one place a mismatch would silently 404 everything.
- **Session detection on the client**: since the cookie is `HttpOnly` (unreadable from JS by design, per the security constraint), the SPA cannot check "am I logged in" by reading the cookie. It infers auth state from API responses: a successful `GET /jobs` on app load means authenticated; a `401` from any call means not. `AuthContext` starts in an "unknown" state and resolves via a single `GET /jobs` probe on mount for protected routes (cheap, and it's data the job-list screen needs anyway) — not a dedicated `/auth/me` endpoint, since none exists and adding one is a backend change out of this spec's scope.

2. **API client — typed fetch wrapper + domain types**
   - Files: `web/src/api/types.ts`, `web/src/api/client.ts`, `web/src/api/client.test.ts`
   - What: `types.ts` — `Job`, `Participant`, `Metric`, `JobDetail` (mirroring the Go wire shapes exactly, field-for-field, as the single source of truth other modules import rather than redeclare, per frontend skill rule 7). `client.ts` exports one function per endpoint: `requestOtp(phone)`, `verifyOtp(phone, code)`, `logout()`, `listJobs()`, `createJob(youtubeUrl)`, `getJob(id)`. Internally, one `apiFetch(path, init)` helper: prefixes `/api`, sets `credentials: "same-origin"` (cookie must ride along), and on non-2xx: reads `response.text()` and throws an `ApiError { status, message }`; a **global 401 hook** — `apiFetch` calls a caller-supplied `onUnauthorized()` callback before throwing when `status === 401`, so any consumer (the router shell in step 4) can react without every call site checking status codes itself. No retry, no intercenal caching.
   - Test first (red): `client.test.ts` stubs global `fetch` (a hand-written fake per call, not a mocking library, per frontend skill rule 3) and asserts: success path resolves with parsed JSON for each of the 6 functions; a `400`/`409`/`429` response with a plain-text body rejects with an `ApiError` whose `.message` is that exact text (not `"[object Object]"` or a JSON-parse crash); a `401` response both rejects AND invokes the registered `onUnauthorized` callback exactly once; requests include `credentials: "same-origin"`.
   - Implement until green.
   - Verify: `cd web && npm test -- --run client`.

4. **App shell — router, `AuthContext`, protected routes, global 401 handling, logout**
   - Files: `web/src/app/AuthContext.tsx`, `web/src/app/ProtectedRoute.tsx`, `web/src/app/router.tsx`, `web/src/app/router.test.tsx`, `web/src/App.tsx` (rewritten from the step-1 placeholder)
   - What: `AuthContext` holds `status: "unknown" | "authenticated" | "anonymous"` and a `logout()` action; on mount, if `status === "unknown"`, it probes via `listJobs()` — success ⇒ `"authenticated"` (and the result is handed to the job-list screen so it isn't refetched a second time immediately after), any error ⇒ `"anonymous"` (per the "session detection" decision above). It registers itself as the API client's `onUnauthorized` handler: on any 401 from *any* call anywhere in the app, it clears all client-held state (auth status → `"anonymous"`, and any in-memory job cache) and the router redirects to `/login` (criterion 15, edge case 2 — including dropping unsaved form input, since the redirect unmounts the form component entirely rather than preserving it). `ProtectedRoute` renders its children only when `status === "authenticated"`; renders nothing (or a tiny loading state) while `"unknown"`; redirects to `/login` when `"anonymous"` — this is what makes a logged-out deep link to `/jobs/:id` redirect instead of firing the API call (edge case 8) and makes browser back-navigation after logout re-hit `ProtectedRoute`'s check rather than show a cached view (criterion 16), since React unmounts the protected tree on navigation rather than caching it. Routes: `/login` (public, redirects to `/jobs` if already authenticated), `/jobs` (protected, list), `/jobs/new` (protected, submission form), `/jobs/:id` (protected, results), `/` redirects to `/jobs`. A `LogoutButton` calls `logout()` from the API client then `AuthContext`'s `logout()` (clears state, navigates to `/login`) regardless of whether the network call succeeds (logout should never strand a user on an authenticated-looking screen).
   - Test first (red): `router.test.tsx` — rendering the app at `/` while `listJobs` stub rejects (unauthenticated) lands on the login screen and asserts `listJobs`/`getJob` were never called beyond the one probe (criterion 1's "no `/jobs` request" bar is read as "no *additional* request users would notice" given the probe design — see Risks); rendering at `/jobs/999` while logged out redirects to `/login` without calling `getJob` (edge case 8); simulating a `401` from a stubbed call while on `/jobs` redirects to `/login` (criterion 15); clicking logout then pressing browser back does not show the job list without a fresh (stubbed) `listJobs` call (criterion 16 — assert the stub is called again post-back-nav, not that cached data reappears).
   - Implement until green.
   - Verify: `cd web && npm test -- --run app`.
   - **Deviation flag**: criterion 1 says "no `/jobs` request is made" for an unauthenticated root load, but the chosen auth-detection design (no `/auth/me` endpoint exists) means the *first* paint before the probe resolves briefly renders neither screen, and the probe itself is a `GET /jobs` call that will 401 before the login screen shows. This is a deviation from a literal reading of criterion 1 and must be called out explicitly in the implementation commit/PR per `CLAUDE.md`'s rule on surfacing spec deviations — plan B if this is unacceptable: request a dedicated cheap `GET /auth/me` (or reuse `/healthz`-style) endpoint from a backend follow-up spec instead of overloading `/jobs` as the probe.

10. **Record the architecture decision**
    - Files: `docs/decisions.md`
    - What: append `## 006: React SPA served via nginx reverse proxy in a new \`web\` Compose service` — Why: first frontend framework choice for the project, needed to give the existing OTP auth and jobs API a user-facing surface; nginx keeps the SPA and API on one origin so the `SameSite=Strict` session cookie is sent, without needing a shared-domain TLS/cookie workaround. Cost: two runtime images to build or (build+deploy) instead of one; nginx config is one more piece of infra to keep in sync with the API's route surface if routes change.
    - Test first: n/a (documentation-only change).
    - Verify: manual read-through; no automated check applies.
    - Commit: can ride with step 9's infra commit, or its own doc-only commit — either is fine since it has no test dependency on other steps.

    - Verify: push the branch / open the PR and confirm the new `web` job appears in the Checks tab and goes green alongside the existing `test` job — this is the acceptance check for this step, since a workflow file can't be unit-tested locally the way application code can (a `push`/`pull_request` job listing in GitHub Actions is the ground truth).
    - Commit: can ride with step 9's infra commit (both are deployment/tooling, not application code) or its own — either is fine, but must land no later than the PR that first introduces `web/`, so the new suite is never merged un-gated by CI even for one commit.

## Order

Tests precede implementation within every step (steps 1–7), per TDD — no component or hook is written before its failing test exists. Step 1 must land first (nothing else has a toolchain to run in). Step 2 (API client) must precede every feature step (3, 5, 6, 7), since their tests stub the client's exported functions rather than `fetch` directly. Step 4 (router/`AuthContext`) depends on step 3 (auth screens need to exist to route to) and is itself a dependency of steps 5–7 (`ProtectedRoute` wraps all three). Steps 5, 6, and 7 are independent of each other and can be built in any order (or in parallel) once 2 and 4 exist. Step 8 is a cross-cutting gate over 1–7, no new code. **Step 9 (Docker/nginx) is a separate commit from the application code in 1–8** — it has no test dependency on the frontend's internal implementation, only on its build output (`web/dist`) existing, so it can be planned/reviewed independently and is the one step in this plan analogous to `db-migrations`' "migration gets its own commit" rule. Step 10 (decisions.md) has no code dependency and can be committed alongside step 9 or standalone, but must exist before this feature is considered done per the spec's explicit requirement. **Step 11 (CI) must land in the same PR that introduces `web/`** — unlike steps 9/10, it isn't safe to defer to a follow-up, since every commit after step 1 lands frontend code that would otherwise merge to `main` without any CI gate at all.

## Codegen

Not applicable in the sqlc/protobuf/OpenAPI sense — this repo has none of those, confirmed via `go.mod` and file search (same finding as the `user-auth` and `jobs-api` plans). There is, however, a lighter-weight regeneration concern specific to this frontend: **`web/src/api/types.ts` is hand-maintained against the Go handler's wire structs, not generated** — if `internal/handler/jobs.go` or `auth.go`'s JSON field names/shapes change in a future backend spec, `types.ts` must be updated by hand in that same change (flagged here so a future editor doesn't assume a build step keeps them in sync automatically).

## Risks

- **No `/auth/me` endpoint exists, so auth-state detection overloads `GET /jobs`.** Flagged in step 4 as a deviation from a literal reading of criterion 1. Plan B: if this proves confusing in review, split it into its own backend micro-spec (`GET /auth/me` returning just `{user_id}` or `204`/`401`) before finishing step 4 — cheap to add, but it's a backend change this UI spec's non-scope says it shouldn't need, so it's deferred here unless the deviation is rejected.
  - **Resolved:** see `specs/auth-me/spec.md`, which added `GET /auth/me` (behind `SessionMiddleware`, `204`/`401`, no body) and removed this workaround — `AuthContext`'s mount-time probe now calls `getAuthMe()` instead of `listJobs()`, so criterion 1 ("no `/jobs` request is made" on an unauthenticated root load) now holds literally, provable via `router.test.tsx`'s criterion-1 test asserting `listJobs` is never called during that probe.
- **`youtubeUrl.ts`'s client-side validator can drift from the backend's `isValidYoutubeURL` regex** (`internal/handler/jobs.go`) since there's no shared code between Go and TypeScript. A user could hit "client says valid, server says 400" or vice versa. Mitigated by criterion 9 (server error still surfaces inline either way) — this is a UX rough edge, not a correctness bug, since the server remains authoritative. Plan B if drift causes real confusion: extract the accepted-shapes rules into a small JSON/config fixture both step 1's Go tests and the TS tests read from — deferred until there's evidence of actual drift (YAGNI).
- **Error-body format is plain text, not JSON.** If a future backend change wraps errors in a JSON envelope (e.g. `{"error": "..."}`) without updating this plan's assumption, `ApiError.message` would show a literal JSON string in the UI (e.g. showing `{"error":"invalid youtube_url"}` verbatim) instead of a clean message. Step 2's tests pin today's plain-text behavior explicitly so this would fail loudly (a test would need updating) rather than fail silently.
- **`react-router-dom` and any other new `package.json` dependency needs the human sign-off flagged in step 1** before that step is implemented — per frontend skill rule 8. Tailwind is the one exception already cleared (explicitly requested), so it does not block step 1; `react-router-dom` still needs its one-line confirmation.
- **Tailwind v4 is assumed current-stable; version drift is a config-shape risk, not a redesign risk.** If the implementer's `npm install tailwindcss` resolves a major version whose setup differs from the v4 CSS-first approach assumed here (e.g. an environment pinned to v3), step 1's `vite.config.ts`/`index.css` need the v3-style swap noted in the "Concrete values" section (`tailwind.config.js` + `postcss.config.js` + `autoprefixer`) instead — a config change, not a rewrite of any component, since all consumption is via plain utility class names regardless of version.
- **nginx health-check race with `api`.** `web`'s Compose healthcheck only proves nginx itself is serving static files; it does not prove `/api/*` is reachable (that requires `api` to be healthy too, hence `depends_on: api: condition: service_healthy` in step 9 — called out so it isn't dropped as "redundant" during implementation).

## Out of scope guard

Do not touch:
- `internal/*`, `cmd/*` — no Go application code changes; this spec is presentation-only per its Constraints ("no ORM/backend changes... no new Go code, migrations, or business logic"). If a gap is found in the API during implementation (e.g. a genuinely missing field), it gets flagged as a follow-up backend spec, not patched inline here.
- `internal/db/migrations/*.sql` — no schema changes.
- `specs/jobs-api/*`, `specs/user-auth/*`, `specs/walking-skeleton/*` — those specs/plans are already implemented; this plan only consumes their finished API surface.
- Real-time transport (WebSockets/SSE/polling) — explicitly non-scope; do not add a `setInterval` refetch "to make it feel more real-time" even if it seems like a small addition.
- Video embedding/playback, export/share, edit/delete-job UI, pagination, account/profile screens, roles/multi-athlete views, i18n, native mobile — all explicitly non-scope; do not scaffold placeholder routes/components for these "for later."
- A local Vite dev-server Compose service — explicitly non-scope; local dev workflow (e.g. running `npm run dev` on the host, outside Compose) is left to the implementer and is not part of this plan's verification steps.
